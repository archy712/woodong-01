# PRD 생성 프롬프트 — 계모임/동호회 모임 관리 앱

> 이 프롬프트를 Claude Code(또는 Claude Chat)에 그대로 붙여넣어 PRD 초안을 생성하세요.

---

## 프롬프트 본문

당신은 시니어 프로덕트 매니저입니다. 아래 정보를 바탕으로 "계모임/동호회 모임 관리 앱"의 **PRD(Product Requirements Document)**를 작성해 주세요.

### 1. 서비스 개요

- **서비스명(확정)**: 우동 (Woodong) — "우리동호회"의 줄임말이자 친숙한 음식 이름의 언어유희
- **한 줄 정의**: 동호회/모임의 운영, 회비 정산, 투표를 한 곳에서 관리하는 모바일 우선 웹 서비스 (계모임보다 동호회 활동·소속감을 우선 연상시키는 포지셔닝)
- **타겟 사용자**: 동호회/러닝크루/등산모임 운영진(총무), 계모임 총무, 소규모 커뮤니티(10~50명 규모) 멤버
- **핵심 문제**: 현재 엑셀 + 카카오톡 단톡방으로 회비·정산·투표를 관리하며 발생하는 비효율(수기 정산, 미납 파악 어려움, 공지 누락)
- **브랜드/네이밍 가이드**
  - 톤앤매너: 딱딱한 관리툴이 아닌 "친근하고 재미있는 동호회 친구" 느낌 유지
  - 카피 예시: "우동, 모임을 부탁해", "오늘도 우동이 정산해드릴게요"
  - 로고 컨셉: 우동 그릇 모티프 — 그릇 = 모임이 열리는 "자리", 그릇을 둘러싼 사람 아이콘으로 "함께 모이는" 이미지 표현. 컬러는 코럴/앰버 계열(따뜻함, 활기)
  - 도메인 후보: woodong.app / woodong.kr / woodong.co.kr (1순위), woodong.com·uridonghoe.com(브랜드 보호용 확보 권장) — 실제 등록 전 whois.kr, 키프리스(kipris.or.kr) 상표 검색으로 최종 확인 필요

### 1-1. 프로젝트 관리 정보

- **프로젝트 코드네임(내부/개발용)**: `moim-ops` (레포지토리명, 내부 문서용. 사용자 노출 앱 이름은 "우동"으로 분리 운영)

### 2. 기술 스택 (고정 — 변경 제안 불필요)

- Frontend: Next.js (App Router), Tailwind CSS, shadcn/ui, lucide-react
- Backend/DB/Auth: Supabase (PostgreSQL, Auth, Storage, Edge Functions)
- 배포/개발: Claude Code 기반 개발
- 알림 연동: 카카오톡 알림톡 API, Slack Webhook/API, 이메일(예: Resend), 앱 내 알림(종 모양 아이콘 + 알림센터)
- 인증: 이메일/비밀번호, Google OAuth, Naver OAuth, Kakao OAuth

### 3. 핵심 기능 요구사항 (아래 항목별로 상세 User Story + 수용 기준(Acceptance Criteria) 작성)

1. **모임 메인 페이지**
   - 서비스 소개, 사용 기술 스택 소개 섹션 (인포그래픽 스타일)
   - 로그인 전/후 다른 CTA 노출
2. **모임 관리 (CRUD)**
   - 모임 생성/수정/삭제, 멤버 초대(링크 또는 코드), 역할 구분(총무/일반회원)
3. **모임 알림**
   - 공지사항 등록 → 사용자 알림 채널 설정(카카오톡/슬랙/이메일/앱내)에 따라 발송
   - 알림 유형: 공지, 회비 납부 리마인드, 투표 시작/마감, 정산 리포트 발행
4. **회비 관리**
   - 회원별 납부 현황 대시보드(납부/미납/부분납부)
   - 미납자 자동 리마인드 알림(설정 가능한 주기)
   - 지출 내역 등록(카테고리, 영수증 첨부, 담당자)
   - 정산 리포트 자동 생성(기간별 수입/지출/잔액, PDF 또는 웹 뷰 다운로드)
5. **투표 관리**
   - 투표 생성(CRUD), 객관식/찬반, 마감일 설정, 익명/실명 옵션
   - 마감 시 결과 자동 집계 및 알림 발송
6. **인증**
   - 이메일 가입/로그인 + Google/Naver/Kakao 소셜 로그인
   - 소셜 로그인 계정과 이메일 계정 연동/병합 정책 포함
7. **디자인 시스템**
   - shadcn/ui 컴포넌트 최대 활용, lucide 아이콘 일관 사용
   - 모바일 UI/UX 우선 반응형 (360px~ 기준)
   - 데이터 시각화는 인포그래픽 스타일(차트/진행률 바 등)로 표현
8. **푸터 특수 요구사항**
   - lucide 아이콘 전체 리스트업 페이지(아이콘 검색 가능)
   - 컴포넌트 갤러리 페이지 (shadcn/ui 전체 컴포넌트 사용 예제 데모)
   - 이 두 페이지는 개발자/QA용 내부 문서 성격임을 명시

### 4. 비기능 요구사항

- 성능: 모바일 3G/LTE 환경 기준 초기 로딩 목표치 제시
- 보안: Supabase RLS(Row Level Security) 정책 설계 방향 포함
- 확장성: 향후 모임 유형 다양화(스터디, 취미모임 등) 대비 데이터 모델 유연성
- 알림 발송 실패 시 재시도/폴백 정책

### 5. 데이터 모델 (ERD 수준)

- 주요 테이블 초안 제시: users, groups, group_members, dues(회비), payments, expenses, settlements(정산), votes, vote_options, vote_responses, notifications, notification_preferences
- 테이블 간 관계와 주요 컬럼(타입 포함) 명시

### 6. 화면 목록 (IA/사이트맵)

- 인증 플로우, 모임 목록/상세, 회비 대시보드, 지출 등록, 정산 리포트, 투표 목록/상세/결과, 알림센터, 마이페이지(알림 설정), 아이콘 리스트, 컴포넌트 갤러리

### 7. MVP 범위 정의

- **1차 MVP(4주 내 개발 가능한 수준)**에 포함할 기능과 **2차 확장**으로 미룰 기능을 구분해서 제안
- 우선순위는 "총무의 반복 업무 자동화"에 가장 크게 기여하는 기능 순으로 정렬

### 8. 성공 지표(KPI)

- 예: 주간 활성 모임 수, 회비 납부율 개선폭, 알림 클릭률, 총무 1인당 정산 소요시간 감소

### 9. 리스크 및 결정 필요 사항

- 카카오톡 알림톡 API 비즈니스 계정/템플릿 검수 이슈
- 회비/정산 데이터의 금융 정보 취급 시 법적 고지 필요 여부
- 소셜 로그인 3종 + 이메일 계정 통합 시 이메일 중복 처리 정책

## 출력 형식 지침

- 마크다운 문서로 작성, 섹션별 번호와 소제목 유지
- User Story는 "~로서, ~하고 싶다, 왜냐하면 ~이기 때문이다" 형식 사용
- 수용 기준은 Given/When/Then 형식 권장
- 데이터 모델은 표 형식으로 정리
- 전체 분량은 실제 개발 착수가 가능한 수준으로 충분히 상세하게 (섹션 생략 금지)
